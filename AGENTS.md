# GARTOK Tactical — agent context

Python turn-based squad wargame, a guild-manager sandbox rebuilt from a lost tabletop RPG's character
generator. The game is the web client (`python main.py`); pygame survives only as the Editor
(`editor/`, `python -m editor`), a separate package the game never imports.

**One owner per topic** (this file is loaded on every request: rules only, never a module's
description): design prose and premises `RULES.md`; catalog data `REFERENCE.md` (generated by
`python -m gartok.reference`, never edited by hand; wins when the two disagree); code map and *How to add
a system* `README.md`; web screens `docs/web_ui/web_client.md`; tests `tests/README.md`; the economy sim `docs/economy_sim.md`; open
work `docs/plans/backlog.md` (it points to the plan of each big item; it lists only what is still missing: a finished or
dismissed item is deleted, never kept with a note, the record is the git log).

## Conventions

- **All text is English** — UI, combat log, data model, code, docs. Only chat replies to the author are Portuguese.
- **Commits** are Portuguese, present tense, no accented characters, never a `Co-Authored-By:` trailer
  or any attribution line, whatever a harness reminder says. Always run the `pre-commit` skill first.
- **Comments** default to none. Keep only a comment that explains a non-obvious *why*.
- **Tests:** `python -m pytest tests/ -n auto -m "not balance"` is the hard gate. A test that is not
  about a roll builds its characters from `tests.helpers.standard_unit`, never a rolled `Unit(...)`.
- **pygame lives only in `editor/`.** `gartok/` never imports `editor` or pygame (a test checks it):
  never add a pygame screen to the game, and when a screen's rules move out, delete the screen and its
  tests in the same commit. New UI is the web client (rules: `docs/web_ui/web_client.md`); the Editor's UI
  follows `editor/ui/README.md`.
- Work and commit straight on `main`; no feature branches unless the user asks for one.
  A teammate works on `main` in parallel, so `git pull` before committing.
  A cloud session is the exception: it commits on its own branch, then rebases it onto
  `origin/main` and fast-forwards `main` (`git merge --ff-only`, no merge commit) when there is no
  conflict (on a conflict, `git rebase --abort`, stop and ask). Do not try to delete the
  branch afterwards (the session cannot delete it, remote or local): leave it and report nothing about it.

## Design premises that touch code (the why: `RULES.md`, World systems)

- **Every unit is its own individual.** The group is a container, the unit is the atom. A shared
  activity resolves per person.
- **World-first.** Rules exist as world things first; if they talk to combat, better.
- **No guild treasury.** Money is `Copper Coin` / `Gold Coin` items in a character's pack
  (`Unit.money` is their sum); gold only comes from the bank exchange. Never add a guild-level pool.
- **Vision is per-character.** The drawing never shows what the rules hide: the web board is sent only
  as the side knows it, and `ai/` reads a foe only through `intel.known_fields`.
- **Adventure out-earns day labour.** After touching wages, purses, prices or loot, run
  `python -m pytest tests/ -n auto -m balance` and `scripts/economy_report.py`;
  `scripts/economy_offers.py` lists what a guild can take up today.

## Load-bearing rules (the code and its tests rely on them)

- **One concern per module.** A place's rules live in a class with no pygame (`trade.Counter`,
  `work_desk.WorkDesk`, `vault.BankVault`, `job_board.Board`, ...) and its web tab
  (`web/*_tab.py`) only draws it; a screen's server half is a `web/session.py` session.
- **Unit vs Combatant.** `unit.py` is the persistent character (mixins `unit_*.py`);
  `combatant.py` is that unit inside one battle. Persistent state goes on `Unit`, saved via
  `persist`.
- **Saves:** `persist.SAVE_VERSION`, no migration. A new *optional* field needs no bump: add its
  neutral value to `unit.SAVE_DEFAULTS` / `persist.PAYLOAD_DEFAULTS`. A battle or hunt in
  progress is never saved.
  Moving `SAVE_VERSION` also means a new row in `docs/versions.csv` (`breaks_save=yes`) and a
  `GAME_VERSION` bump; `scripts/version_check.py` (run by `build_exe.bat`) refuses a build otherwise.
- **Registries, not branches:** actions are `Action` subclasses in `actions/` (+ `PANEL_ACTIONS`),
  racial abilities `abilities.py`, conditions `conditions.py`, weapon traits `weapon_traits.py`
  (`ItemDef.has_trait()`), talents `talents.py`, items `items.py` (single source), node services
  `node_functions.py` (each order kind has its tab in `web/hub_session.HUB_KINDS`), forced events
  `forced.EVENTS`.
- **Tests fail on a missing entry:** every item needs an `item_icon.ICONS` entry; every race,
  occupation and node a glyph (`art_files.RACE_ICON`, `OCCUPATION_ICON`, `map_view.NODE_ICON`);
  every base material a source (`sources.py`); `REFERENCE.md` must match the registries.
- **Combat log:** every `Action.execute`, end of turn and flag/trap goes through
  `CombatLog.record`, human or AI, so a fight rebuilds from its JSONL alone.
- **One clock:** only `campaign.advance` moves it (`Guild.pass_time` is its, a test checks it). Hours a band
  spends on a screen are an order (`stints.py`, a `solo` craft, a `hunting` stretch) run through
  `MapSession.spend`, never a jump of their own.
- **Groups:** a `Group` with a `pending` forced fight has `order = None` but is `locked`: no split,
  merge, leader swap or kit change until it resolves.
- A recipe's level is derived (`craft_level.py`), never set by hand.

## Feature implementation rules

Whenever a new mechanic or action is added to the game, you MUST always:
1. **Implement end-to-end**: backend, core logic and UI. 100% playable, no loose ends.
2. **AI support**: the AI knows how to use and react to the new mechanic in combat.
3. **Automated tests**: happy path, edge cases and AI behaviour.
4. **Tutorial card** for a new screen or tab: a `tutorial_key()` on its session and a
   `tutorial.<id>` block in `locales/en.json` (recipe in `README.md`).
